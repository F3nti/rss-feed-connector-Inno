# Ziel

Entwicklung einer innovaphone App auf Basis der JavaScript Runtime.

Die App importiert RSS-Feeds und veröffentlicht neue Einträge automatisch in
Connect. Feeds werden in der App-Platform-Datenbank verwaltet; GUIDs verhindern
erneute Posts nach Feed-, Service- oder App-Neustarts.

---

```text
RSS Feed
    ↓
```

# Services API

Discovery erfolgt über:

```json
{
    "api": "Services",
    "mt": "SubscribeServices"
}
```

Login erfolgt über:

```json
{
    "api": "Services",
    "mt": "GetServiceLogin"
}
```

Die SDK-Dokumentation bestätigt `PbxApi("Services")` für Discovery und
`AppWebsocketClient` für die Serviceverbindung. Das PBX-App-Objekt muss die
Services API sowie die Berechtigung für `messages-api` aktiviert haben.
Siehe [Services protocol](https://sdk.innovaphone.com/15r1/doc/appwebsocket/Services.htm)
und [AppWebsocketClient](https://sdk.innovaphone.com/15r1/doc/javascript/AppWebsocketClient.htm).

# Messages Protocol

## Post

```json
{
    "mt": "Post",
    "topic": "connect?technik",
    "text": "<h3>Titel</h3>",
    "tags": [
        "security",
        "news"
    ]
}
```

Wichtige Felder:

```text
topic
text
tags
notify
attach
author
```

Das Messages-Protokoll verwendet auf der AppWebsocket-Verbindung kein
`api`-Feld. Die RSS-GUID wird erst nach erfolgreichem `PostResult` gespeichert.
Siehe [Messages protocol](https://sdk.innovaphone.com/15r1/doc/appwebsocket/Messages.htm).
`MessagesClient.readTopics()` delegiert an `TopicDiscovery`, das `Topic`-
Indikationen bis zum
korrespondierenden `ReadTopicsResult` und gibt SIP-URI, Anzeigename und
optionale Topic-ID zurück.

# Bereits erstellt

## scheduler.js

Scheduler-Konzept:

```javascript
scheduler.start(callback);
scheduler.stop();
scheduler.runNow(callback);
```

Verwendet bevorzugt `Timers.setTimeout()`/`Timers.clearTimeout()` der Runtime;
lokale Tests koennen auf globale Timer zurueckfallen.

```javascript
Timers
```

## RSS Downloader

Verwendet `HttpClient.request("GET", url)` asynchron mit `onrecv`, `recv`,
`oncomplete` und `onerror`. `fetch()` wird nicht vorausgesetzt. Vor jedem
Abruf validiert `RssUrlPolicy` den URL-Host und alle DNS-Antworten auf
öffentliche IPv4-/IPv6-Adressen; private Ziele und HTTP-Redirect-Antworten
werden abgelehnt. Die Runtime bietet keine dokumentierte DNS-Pinning-Option,
deshalb sollte ausgehender Netzwerkverkehr zusätzlich auf PBX-/Plattformebene
beschränkt werden, um DNS-Rebinding vollständig abzufangen. Antwortmetadaten
und maximal die ersten acht Byte werden einmal pro Antwort protokolliert; nie
den Feed-Body oder vertrauliche Request-Daten loggen.

## RSS Parser

`RssParser.parse(xml)` verarbeitet RSS 2.0 und Atom ohne `DOMParser`.
Lokale Fixtures und Tests liegen unter `test/`.

## Duplicate Detection und Messages API

`RssEntryRepository` lädt bekannte GUIDs pro Feed gezielt und in begrenzten
SQL-Batches aus der App-Platform-Datenbanktabelle `rss_entries`, statt bei
jedem Poll die gesamte Feed-Historie in den Speicher zu laden. Der Service
überspringt bereits gespeicherte Einträge, begrenzt gleichzeitige Messages-
Posts auf vier und speichert eine GUID erst nach erfolgreichem `PostResult`.
Datenbankfehler beim Laden verhindern den Feed-Post; Fehler beim Speichern nach
einem erfolgreichen Post werden protokolliert und als fehlgeschlagener Lauf
gemeldet. `ServicesClient` abonniert die Services API, sucht `messages-api`,
fordert Login-Parameter für den AppWebsocket-Challenge an und authentifiziert
die Verbindung. `MessagesClient` sendet `Post`-Anfragen, korreliert Antworten
über `src` und meldet ausbleibende `PostResult`-Antworten nach 30 Sekunden als
Fehler. `HtmlBuilder` übernimmt zulässige HTML-Formatierung aus RSS-
Beschreibungen und entfernt unsichere Elemente, Attribute und URLs. Vor dem
Schedulerstart prüft der Dienst das konfigurierte Ziel mit `ReadTopics()`. Ist
das Topic für die Verbindung nicht erreichbar, startet er den Feed-Zyklus nicht
und protokolliert die verfügbaren SIP-URIs. Optionale Ablehnungsgründe aus
`PostResult` werden ebenfalls protokolliert.

Nach erfolgreicher Topic-Prüfung startet der Scheduler den ersten Feed-Zyklus
sofort und wiederholt ihn anschließend im konfigurierten Intervall.

## myApps-Oberfläche und Feed-Einstellungen

Die myApps-Nutzer-App verwaltet mehrere Feeds mit URL, Connect-Topic, Tags,
Intervall und Aktivstatus. Topics werden live über `ReadTopics` ermittelt; die
angezeigte Domain und App-Identität stammen aus dem myApps-Login. Feed-Daten
liegen gemeinsam in der App-Platform-Datenbank-Tabelle `rss_feeds`. Die
Konfiguration ist fuer die einzelne App-Instanz gedacht; gemäß Nutzerwunsch
soll die myApps-App nur dem Administrator zugewiesen werden. Der Feed-Service
aktualisiert seine Scheduler nach Änderungen; der Abrufstatus ist bis zum
Neustart im Speicher.

Die `apps.json`-Route stellt die App-URL innerhalb der bestehenden App-Instanz
bereit. Zum Starten aus myApps muss auf der PBX zusaetzlich ein App Object mit
dieser URL angelegt und dem Administrator zugewiesen werden. `apps.json` legt
kein App Object automatisch an und konfiguriert kein Launcher-Icon. Das Logo
liegt als SVG fuer die Oberflaeche und PNG-Datei bereit.
Die benoetigten Browser-SDK-Dateien `lib1` und `appwebsocket.Connection`
liegen im HTTP-Dateipaket unter `web1/` und werden relativ zur App-URL geladen.
`build.txt` und `label.txt` definieren Buildnummer und Alpha-Kennzeichnung im
AP Manager. Das 100x100-PNG neben dem App-Binary wird mit dem Runtime-Paket
bereitgestellt; es setzt nicht automatisch das App-Store-Service-Logo. Dieses
Logo muss im App-Store-Eintrag als Icon hinterlegt werden. `apps.json` definiert
nur App-URLs, keine App-Store-Darstellung.
Das kombinierte Connect/RSS-Logo liegt als SVG für die GUI und als PNG für die
App-Platform-Pakete vor. Beide Icon-Dateien müssen beim Erstellen des Pakets
gemeinsam mit `dist/httpfiles` und den Architekturverzeichnissen synchronisiert
werden.

# Implementierte Verarbeitungspipeline

## `rss-downloader.js`

Ruft Feeds mit `HttpClient.request("GET", url)` ab, validiert zuvor URL und
DNS-Ziel und lehnt Redirects ab. Antwortdaten werden inkrementell decodiert;
TextDecoder wurde beim erfolgreichen Feed-Lauf verwendet. Für andere
PBX-/Runtime-Versionen die Verfügbarkeit erneut prüfen.

## `rss-parser.js` und `html-builder.js`

`RssParser.parse(xml)` verarbeitet RSS 2.0 und Atom. `HtmlBuilder` erzeugt
Connect-kompatibles HTML und filtert unsichere Elemente, Attribute und URLs.

## Datenbank, Deduplizierung und Messages API

`rss-feed-repository.js` verwaltet Feeds; `rss-entry-repository.js` lädt
bekannte GUIDs in begrenzten SQL-Batches und speichert erfolgreiche Einträge.
Der Service begrenzt gleichzeitige Posts auf vier und persistiert eine GUID
erst nach erfolgreichem `PostResult`.

`services-client.js` übernimmt Services-Discovery und Login;
`topic-discovery.js` ermittelt erreichbare Topics; `messages-client.js`
korreliert Requests und Antworten. Der Scheduler startet nach erfolgreicher
Topic-Prüfung sofort und führt weitere Zyklen im konfigurierten Intervall aus.

# Verifizierter Stand und verbleibende Runtime-Prüfungen

Ein Lauf des Golem-Atom-Feeds bestätigte URL-Zielprüfung, HTTP 200 mit
`application/atom+xml`, erfolgreiches Parsing und `40 duplicates, 0 failed`.
Dieser Lauf hat keinen neuen Beitrag gepostet und ist daher kein Nachweis für
einen erfolgreichen neuen Post.

Vor einem Release auf der Ziel-PBX noch einen Feed-Eintrag mit einer bislang
unbekannten GUID durch den vollständigen Posting-Pfad testen und
`PostResult`/Fehlerverhalten verifizieren. Attachments sind nicht implementiert.

# Git und Tests

Tests lokal ausführen:

```bash
node --test test/*.test.js
```

Vor einem Commit `git status` prüfen, nur auf Wunsch committen und den
Co-authored-by-Trailer des Repository-Kontexts beibehalten.

Wenn Runtime-Dateien geändert werden, `config.json`-Ladereihenfolge prüfen und
die HTTP-Dateien sowie Pakete für alle unterstützten Architekturen synchron
halten. Lokale Tests decken nicht alle Besonderheiten der PBX-Runtime ab.
